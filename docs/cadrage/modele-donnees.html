I · Vue d'ensemble

Le plan tient : vingt-quatre tables, une seule règle d'accès

Le schéma garde l'approche « tables dédiées par outil » ; il précise les clés, sort trois JSON et ajoute ce que Supabase attend.

NouveauModifiéInchangéFlèche : de la clé étrangère vers la table visée · pointillé : lien polymorphe

II · Les conventions communes

Chaque table hérite des mêmes colonnes et de la même policy

Ces conventions font le gros du lot 2 : une fois posées, chaque outil les recopie.

Les pierres tombales servent la synchronisation

Modifié

Suppression = UPDATE

Le plan supprimait physiquement les items. Un téléphone resté hors ligne ne verrait jamais la suppression en relisant updated_at > curseur.

Modifié

Realtime filtrable

Avec la RLS, Supabase Realtime ne filtre pas les événements DELETE et n'en donne que la clé. Un UPDATE de deleted_at passe par le même filtre household_id que le reste.

Nouveau

Purge planifiée

Une tâche pg_cron quotidienne supprime pour de bon les lignes mortes depuis 30 jours. Les clés étrangères en cascade font le ménage des enfants.

Une seule règle d'accès

La fonction d'appartenance, puis la policy recopiée sur chaque table 
create function private.is_member(hh uuid)
returns boolean
language sql stable security definer
set search_path = ''
as $$
  select exists (
    select 1 from public.membership m
    where m.household_id = hh
      and m.user_id = (select auth.uid())
  );
$$;

alter table public.checklist_item enable row level security;
create policy membres_du_foyer on public.checklist_item
  for all to authenticated
  using (private.is_member(household_id))
  with check (private.is_member(household_id));

Pourquoi security definer. La fonction lit membership sans repasser par sa propre RLS, ce qui évite la récursion ; (select auth.uid()) est évalué une fois par requête et non par ligne. Variantes : push_subscription et notification_pref filtrent sur user_id = auth.uid(), activity_log n'a qu'une policy SELECT, external_media est lisible par tout compte connecté et écrit par le seul service_role.

Une clé étrangère composite empêche de traverser les foyers

Le parent expose (household_id, id) ; l'enfant y pointe avec les deux colonnes 
alter table checklist add unique (household_id, id);

alter table checklist_item
  add foreign key (household_id, checklist_id)
      references checklist (household_id, id) on delete cascade,
  add foreign key (household_id, category_id)
      references shopping_category (household_id, id)
      on delete set null (category_id);   -- Postgres 15+

Ce que ça garantit. La RLS ne contrôle que le household_id de la ligne écrite ; sans clé composite, un item du foyer A pourrait viser une liste du foyer B. La forme set null (category_id) ne vide que la colonne visée, pas household_id.

VII · Dépenses partagées

Les comptes se calculent, ils ne se stockent pas

Quatre tables et une vue, façon Tricount : des carnets, des dépenses, des parts et des remboursements.

Nouveau

Des centimes entiers

Montants en bigint, dans l'unité mineure de la devise. La somme des parts se compare à l'égalité stricte, sans flottant.

Nouveau

Un taux figé

Le taux vers la devise du carnet est enregistré à la saisie. Un solde d'hier ne bouge pas quand l'euro bouge.

Nouveau

Des soldes calculés

Rien n'est stocké : la vue expense_balance additionne dépenses, parts et remboursements. Un solde ne peut donc pas diverger.

expense_balance : chaque mouvement d'argent devient un flux signé 
create view expense_balance with (security_invoker = true) as
with flux as (
  select household_id, book_id, paid_by as user_id, book_amount_cents as cents
    from expense where deleted_at is null
  union all
  select e.household_id, e.book_id, s.user_id, -s.share_cents
    from expense_share s join expense e on e.id = s.expense_id
   where e.deleted_at is null
  union all
  select household_id, book_id, from_user, amount_cents
    from settlement where deleted_at is null
  union all
  select household_id, book_id, to_user, -amount_cents
    from settlement where deleted_at is null
)
select household_id, book_id, user_id, sum(cents)::bigint as balance_cents
from flux group by household_id, book_id, user_id;

Journal et push. log_activity couvre expense et settlement avec tool_key = 'expenses' ; entity_label garde « Restaurant Alfama · 42,00 € ». Le push dit la part de l'autre : « ta part : 21,00 € ».

VIII · Les outils futurs

Un nouvel outil s'ajoute sans toucher au socle

Trois outils candidats, branchés par des clés qui partent d'eux.

Le contrat d'un nouvel outil

1
Ses tables. Les sept colonnes communes, et une clé composite vers chaque parent.
2
Une policy par table. La même is_member(household_id), recopiée.
3
Deux triggers par table. touch_row et log_activity : l'historique et les push suivent seuls.
4
Une clé de registre. Une ligne dans tools/registry.ts et une dans tool_activation au seed.
Dépenses a suivi ce contrat. expense_book.trip_id et expense.booking_id partent du nouvel outil vers Voyages : ni trip ni booking n'ont changé (voir VII).

La clé étrangère vit toujours du côté de l'outil qui arrive : le nouveau pointe vers l'ancien, jamais l'inverse.

OutilSes tablesOù il se brancheVersion

Pourquoi les CHECK du socle sont des expressions régulières. tool_key, entity_type et action acceptent toute clé bien formée : un nouvel outil n'a ni enum à étendre ni contrainte à réécrire.
